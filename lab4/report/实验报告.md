## 一、实验目的

本实验围绕内核线程的创建与执行展开，在已有物理内存管理和中断处理能力的基础上，建立从页表映射、线程初始化到调度切换的完整运行过程。主要目标包括以下六项。

1. **掌握虚拟页映射的维护方法。** 理解 Sv39 页表项中物理页号、有效位和权限位的作用，实现指定虚拟地址的映射建立、更新与撤销，分析同一物理页重复映射和不同物理页替换时的处理方式。

2. **理解内存资源的引用与回收。** 结合物理页引用计数，掌握共享映射、解除映射和页面释放之间的关系，并理解修改页表后执行 TLB 失效操作的必要性，使页表、引用计数和处理器缓存保持一致。

3. **掌握内核线程的组织形式。** 理解进程控制块、内核栈、陷阱帧和上下文各自保存的信息，完成 PCB 初始化、PID 分配、父子关系设置和进程链表登记，创建空闲线程 `idleproc` 与初始化线程 `initproc`。

4. **理解线程首次运行的启动机制。** 分析 `kernel_thread`、`copy_thread` 与汇编入口之间的配合，通过预先构造寄存器现场，使新线程能够经过陷阱返回路径进入指定函数，并正确取得参数。

5. **掌握基本调度与上下文切换。** 实现按进程链表顺序选择可运行线程，理解临界区保护、`current` 更新、Sv39 页表切换及寄存器恢复的先后关系，观察内核线程之间如何交接 CPU 使用权。

6. **形成结合源码与运行结果的分析方法。** 使用 QEMU 4.1.1 运行自动评分，通过页映射、线程创建和调度三类检查验证实现，并在 AI 协作中练习接口核对、代码审查和故障定位。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

Lab4 的核心主题是内核线程管理。前面的实验已经让内核能够管理物理页面、响应中断和恢复异常现场，本实验进一步把执行中的程序组织为具有独立身份与运行现场的线程，并让多个线程共享处理器。

1. **建立可以维护的地址映射。** 内核通过页表访问物理内存，映射的建立和撤销会同时影响页表项、页面引用和 TLB。模块一补齐这部分操作，使后续访问内核栈、PCB 和其他数据时具备可靠的内存管理基础。当前内核线程共享启动页表，各线程使用的栈仍分别占用独立的内存区域。

2. **把线程入口组织成可运行实体。** 一个函数要成为内核线程，需要配套的 PCB、内核栈、初始寄存器现场、PID 和调度状态。模块二将这些资源组合起来，先把已有启动现场登记为 `idleproc`，再创建以 `init_main` 为入口的 `initproc`。线程创建完成后，其信息进入进程链表，调度器便能发现它。

3. **把保存的现场恢复为实际执行。** 模块三从链表中选择处于 `PROC_RUNNABLE` 状态的线程，更新当前线程指针和页表，再恢复目标线程的寄存器。线程第一次运行时使用创建阶段准备的现场，以后再次运行时使用上一次切出时保存的现场。

主要执行关系如下。

```text
kern_init()
    ├─ pmm_init()             物理内存、页表与内核分配器初始化
    ├─ pic_init() / idt_init() 中断控制与陷阱入口初始化
    ├─ vmm_init()             虚拟内存管理结构检查
    ├─ proc_init()
    │    ├─ 登记 idleproc，设置 current
    │    └─ kernel_thread(init_main, ...)
    │         └─ do_fork()
    │              ├─ alloc_proc() / setup_kstack()
    │              ├─ copy_mm() / copy_thread()
    │              └─ 分配 PID、登记链表、唤醒线程
    ├─ clock_init() / intr_enable()
    └─ cpu_idle()
         └─ schedule()
              └─ proc_run()
                   └─ switch_to()
                        └─ forkret → forkrets → __trapret
                             └─ kernel_thread_entry → init_main
```

这条链路连接了内存管理、进程管理和异常返回三个部分。`proc_init` 负责准备资源和状态，`schedule` 负责选择运行对象，`switch_to` 与陷阱返回路径负责真正改变执行位置。分析时需要同时关注线程保存在哪里、何时进入可运行状态，以及处理器最终从哪个地址继续取指。

执行过程中，`current` 表示正在运行的线程，`proc_list` 记录普通线程，`idleproc` 作为无其他可运行线程时的选择。进程散列表则支持根据 PID 查找 PCB。链表、散列表和当前线程指针承担不同访问需求，它们共同把内核中的线程资源组织成可查询、可调度的整体。

### 3.2 功能的逐步实现

1. **先衔接物理内存管理和陷阱处理。** Lab2 中的页面分配与回收为页表、PCB 和内核栈提供内存，Lab3 中的寄存器保存恢复机制为后续线程启动提供基础。迁入这些代码时，需要核对 Lab4 的数据结构、地址常量和入口符号，使旧功能能够继续被当前框架调用。

2. **完善页表插入与删除。** `page_insert` 根据虚拟地址定位叶子项，处理新建映射、替换旧映射和更新权限。`page_remove` 解除已有映射，并在页面引用归零时回收物理页。这一步先完成，是因为线程资源的管理依赖稳定的内存访问环境，页表测试也会在启动阶段运行。

3. **建立 PCB 和内核栈。** `alloc_proc` 设置线程初始字段，`setup_kstack` 分配运行时使用的内核栈。`do_fork` 将这些资源与父进程、PID、链表节点联系起来。资源准备和登记分阶段进行，可以让调度器看到的线程具备完整的运行条件。

4. **构造首次执行现场。** `kernel_thread` 在临时陷阱帧中记录函数入口、参数和状态寄存器，`copy_thread` 把陷阱帧安放到新线程栈顶，并设置 `context.ra` 与 `context.sp`。只有把首次运行路径准备好，线程被选中后才能沿正确入口执行。

5. **完成系统初始线程的登记。** `proc_init` 初始化进程管理结构，将现有启动栈交给 PID 为 0 的 `idleproc`，再创建 PID 为 1 的 `initproc`。`idleproc->need_resched` 初始置位，使内核进入空闲循环后可以立即发起调度。

6. **接入调度和寄存器切换。** `schedule` 选择目标，`proc_run` 同步当前线程与地址空间，`switch_to` 保存和恢复寄存器。完成这一步后，之前建立的 PCB、栈和陷阱帧便转化为真实的线程执行过程。评分中的多个测试线程主动调用 `schedule`，用于检查切出、切入和恢复执行能否连续进行。

### 练习：[功能模块一：虚拟内存页操作功能]

**负责人：** [2410867-于润泽]

#### 模块功能描述

**需要实现/修改的函数：**

```c
int page_insert(pde_t *pgdir, struct Page *page, uintptr_t la, uint32_t perm);
void page_remove(pde_t *pgdir, uintptr_t la);
```

**功能说明：**

1. **模块作用与输入信息。** 本模块位于 `kern/mm/pmm.c`，负责维护虚拟页到物理页的映射。`pgdir` 是页表根的内核虚拟地址，`la` 是待操作的虚拟地址，`page` 指向目标物理页的描述符，`perm` 给出所需权限。`page_insert` 成功时返回 0，页表分配失败时返回 `-E_NO_MEM`。`page_remove` 完成撤销操作后返回。

2. **定位页表项并准备页表资源。** 插入映射首先调用 `get_pte(pgdir, la, 1)`。该函数利用各级索引向下查找，在下级页表缺失时申请一个物理页、清零并建立上级指向它的表项。最终返回叶子页表项的地址。若当前调用新分配了一层页表，而下一层分配失败，则恢复原来的上级表项、刷新相关翻译状态并释放新页，避免保留未完成的页表路径。

3. **处理新建、重复和替换映射。** 取得页表项之后，先给目标页增加一次引用，再检查旧项。如果旧项指向同一物理页，就抵消刚才的临时引用，使引用总数保持原值。如果旧项指向其他物理页，则解除旧映射，减少旧页引用，在归零时回收。最后使用 `pte_create(page2ppn(page), perm)` 写入新的页表项。先增加新页引用的顺序，使同页更新权限的过程中始终保有该页的有效引用。

4. **撤销映射与回收页面。** `page_remove` 使用 `create=0` 查找，页表路径不存在时直接结束。存在叶子项时交给内部辅助函数 `page_remove_pte` 处理。辅助函数先检查有效位，再取得旧页描述符、清除表项并使对应 TLB 项失效，随后减少引用计数。物理页仍被其他地址映射时继续保留，引用计数归零时通过 `free_page` 交回分配器。

5. **同步页表、权限与 TLB。** 页表在内存中的内容更新后，处理器可能还缓存着旧地址翻译，因此插入、替换和撤销都需要调用 `tlb_invalidate`。当前实现使用带目标地址的 `sfence.vma`，并通过汇编的 `memory` 约束告知编译器相关内存访问顺序。权限变化同样需要同步，才能使后续访问遵守新设置。

几种操作对引用计数的影响可以放在一起观察。

| 操作场景 | 页表项变化 | 引用计数变化 | 回收条件 |
|------|------|------|------|
| 空地址映射到页 A | 建立指向 A 的有效项 | A 增加 1 | 无旧页需要回收 |
| 原来指向 A，再次插入 A | 更新权限等表项内容 | A 保持原值 | A 继续被此地址引用 |
| 原来指向 A，改为 B | 旧映射被 B 替换 | A 减少 1，B 增加 1 | A 的引用归零时回收 |
| 删除指向 A 的映射 | 清除有效项 | A 减少 1 | A 的引用归零时回收 |
| 删除未映射地址 | 保持无映射状态 | 计数保持原值 | 无页面需要回收 |

例如，物理页 A 同时映射到两个虚拟地址时，引用计数为 2。撤销其中一个地址后，计数变为 1，剩下的地址仍可访问 A。撤销第二个地址后，计数变为 0，页面才可以重新分配。若直接覆盖旧 PTE 而忽略引用变化，就可能让旧页失去映射却一直无法回收。

本模块通过 `get_pte` 衔接多级页表，通过页引用接口和 `free_page` 衔接物理内存管理器。叶子映射的删除保留中间页表页，其余地址仍能沿已有页表路径查找。评分中的重复插入、映射替换和重复删除场景，分别检查了上述不同状态变化。

### 练习：[功能模块二：进程创建及初始化功能]

**负责人：** [2410867-于润泽]

#### 模块功能描述

**需要实现/修改的函数：**

```c
static struct proc_struct *alloc_proc(void);
void proc_init(void);
int kernel_thread(int (*fn)(void *), void *arg, uint32_t clone_flags);
int do_fork(uint32_t clone_flags, uintptr_t stack, struct trapframe *tf);
static void copy_thread(struct proc_struct *proc, uintptr_t esp, struct trapframe *tf);
static int copy_mm(uint32_t clone_flags, struct proc_struct *proc);
```

**功能说明：**

1. **PCB 初始化。** `alloc_proc` 从内核堆取得 `struct proc_struct`，清零后设置 `state=PROC_UNINIT`、`pid=-1` 和 `pgdir=boot_pgdir_pa`，并初始化进程链表节点与散列表节点。此时线程尚处于资源准备阶段，`parent`、`mm`、`tf` 等字段为空，运行次数和调度标志为零。后续创建过程逐步填充这些字段。

2. **内核线程入口包装。** `kernel_thread` 先构造一个清零的临时陷阱帧，将函数 `fn` 存入 `s0`，将参数 `arg` 存入 `s1`，将 `epc` 设为 `kernel_thread_entry`。状态寄存器中设置 `SPP` 和 `SPIE`、清除 `SIE`，使线程经 `sret` 后在 S 态执行并打开中断。随后调用 `do_fork`，由统一创建流程申请资源并返回 PID。

3. **线程资源的申请与登记。** `do_fork` 先检查进程数是否达到 `MAX_PROCESS`，再申请 PCB、设置父进程、分配内核栈，调用 `copy_mm` 和 `copy_thread` 准备运行环境。准备完成后进入临界区，分配 PID、加入散列表和进程链表、增加进程数，再调用 `wakeup_proc` 设置为 `PROC_RUNNABLE`。此时调度器能够取得的 PCB 已具备有效的栈和初始现场。

4. **创建失败时的资源处理。** 达到数量上限时返回 `-E_NO_FREE_PROC`，内存申请失败时返回 `-E_NO_MEM`。如果 PCB 成功而内核栈分配失败，就释放 PCB；如果已经分配内核栈而后续准备失败，则先释放内核栈，再释放 PCB。失败分支发生在登记之前，因此无需从进程链表中移除半初始化的线程，进程数也保持原值。

5. **共享地址空间与独立内核栈。** 本实验的内核线程都使用 `boot_pgdir_pa`，`copy_mm` 检查当前线程的 `mm` 为空，并令新线程的 `mm` 保持为空。各线程共享内核地址映射，同时拥有自己的栈空间，用来保存局部变量、函数返回地址和调用过程。切换 `sp` 后，处理器就能继续使用目标线程原来的调用栈。

6. **首次执行现场的布局。** `copy_thread` 把陷阱帧副本放在 `kstack + KSTACKSIZE - sizeof(struct trapframe)` 处，将子线程的 `a0` 置为 0。当传入 `esp=0` 时，陷阱帧里的 `sp` 取陷阱帧起始位置。与此同时，把 `context.ra` 设为 `forkret`，把 `context.sp` 设为陷阱帧地址。这样，底层切换恢复 `context` 后能够先进入返回入口，再恢复陷阱帧中保存的函数入口和参数。

7. **初始线程的建立。** `proc_init` 初始化全局链表和散列表，把当前启动现场组织为 PID 0 的 `idleproc`。它复用 `bootstack`，设置可运行状态与调度请求，并成为 `current`。随后以 `init_main` 和字符串参数创建 PID 1 的 `initproc`，设置名称为 `init`。`initproc` 通过后续调度接管执行，输出自身 PID、名称和收到的参数。

各字段在创建过程中的职责如下。

| 字段或结构 | 保存的信息 | 本实验中的用途 |
|------|------|------|
| `state`、`pid` | 生命周期状态和线程编号 | 区分未初始化与可运行状态，通过 PID 查找线程 |
| `parent` | 创建者的 PCB 地址 | `initproc` 的父线程为 `idleproc` |
| `kstack` | 内核栈底地址 | 为线程的调用栈和初始陷阱帧提供空间 |
| `mm`、`pgdir` | 地址空间描述与根页表物理地址 | 当前线程的 `mm` 为空，`pgdir` 使用启动页表 |
| `context` | `ra`、`sp` 和被调用者保存寄存器 | 支持内核线程之间的现场切换 |
| `tf` | 陷阱帧地址 | 恢复首次执行所需的通用寄存器和状态寄存器 |
| `list_link`、`hash_link` | 两类管理结构的连接节点 | 分别支持调度遍历和按 PID 查找 |

新线程首次运行的衔接过程如下。

```text
kernel_thread(fn, arg)
    把 fn、arg、kernel_thread_entry 写入临时陷阱帧
        ↓
do_fork() → copy_thread()
    陷阱帧复制到新线程内核栈
    context.ra = forkret
    context.sp = 新陷阱帧地址
        ↓
首次 switch_to()
    恢复 context 后 ret 到 forkret
        ↓
forkret() → forkrets(current->tf) → __trapret
    恢复通用寄存器、sstatus 和 sepc，执行 sret
        ↓
kernel_thread_entry
    把 s1 中的参数送入 a0，通过 s0 调用 fn(arg)
```

`context` 和 `trapframe` 在这条路径中先后工作。前者提供切换函数返回的位置和栈，后者提供目标函数运行前的完整寄存器环境。两个结构中的栈地址、返回地址和入口参数相互对应，才能把“线程已经创建”推进到“线程开始执行”。

### 练习：[功能模块三：进程调度]
1．开关中断是怎么实现的？

local_intr_save(intr_flag) 先读取 sstatus 的 SIE 位，保存此前是否开启中断，再清除 SIE 位来关闭中断。`local_intr_restore(intr_flag)` 根据保存的值恢复，原来开启就重新开启，原来关闭就保持关闭。

这样可以支持嵌套临界区，避免内层操作提前打开中断。在本实验的单核环境中，它用于防止中断打断共享数据修改和线程切换。它不会屏蔽同步异常，多核共享数据还需要锁保护。

2．为什么 get_pte() 中两段代码很像？

因为多级页表每一层的操作都相同：根据虚拟地址索引找到当前页表项，检查下一级页表是否存在，不存在且允许创建时就分配、清零，再把地址写入当前项。

Sv32 是两级页表，Sv39 是三级，Sv48 是四级。当前采用 Sv39，访问最低级页表前需要经过两层，所以出现两段相似代码。

三种模式的基本页都是 4 KiB。Sv32 每项 4 字节，每级索引 10 位；Sv39、Sv48 每项 8 字节，每级索引 9 位。若考虑大页，遍历时还需要判断上层条目是否已经是叶子项。

3．查找和分配需要拆开吗？

我认为教学实验中合并是合理的。通过 create 参数控制是否分配，可以复用遍历逻辑，让调用简单。

但在完整内核中，拆分对外接口更清晰，因为纯查询和分配的副作用、失败处理及同步要求不同。可以提供“只查找”和“查找并创建”两个接口，内部共享遍历逻辑。这样既明确调用意图，也避免代码重复。

#### 模块功能描述

**需要实现/修改的函数：**

```c
void cpu_idle(void);
void schedule(void);
void proc_run(struct proc_struct *proc);
void switch_to(struct context *from, struct context *to);
```

**功能说明：**

1. **空闲线程发起调度。** `cpu_idle` 持续检查 `current->need_resched`。该标志在 `idleproc` 初始化时已置位，因此内核进入空闲循环后会调用 `schedule`。当普通线程暂时没有可运行对象时，`idleproc` 提供一个有效的执行现场，处理器可以继续在空闲循环中等待调度需求。

2. **按链表顺序选择线程。** `schedule` 先保存并关闭本地中断，清除当前线程的调度请求。当前线程为 `idleproc` 时，以 `proc_list` 表头作为扫描起点；否则以当前线程的链表节点为起点。每次前进到下一项，跳过表头，选择遇到的第一个 `PROC_RUNNABLE` 线程。到达链表末端后继续绕回，直到找到候选或遍历一轮。

3. **处理空闲和原线程继续运行的情况。** 如果没有找到可运行节点，选择 `idleproc`。如果只有当前普通线程可运行，扫描绕回时会再次选中它。选定线程的 `runs` 增加一次，记录调度选择次数，目标与当前线程相同时直接结束本次选择，目标不同时再调用 `proc_run`。因此 `runs` 反映的是被选择的次数，而具体寄存器切换发生在目标变化时。

4. **更新当前线程和地址空间。** `proc_run` 保存旧 `current`，将目标写入 `current`，再根据目标 PCB 中的页表根物理地址构造 `satp`。Sv39 的模式值为 8，位于寄存器的 63—60 位，页表根物理地址右移 12 位得到物理页号。本次 ASID 为 0。写入 `satp` 后执行 `sfence.vma`，再进入 `switch_to`，使目标线程运行时看到与 PCB 对应的地址空间。

5. **保存和恢复寄存器。** `switch_to` 在 `kern/process/switch.S` 中实现，参数 `a0` 指向旧上下文，`a1` 指向新上下文。汇编依次保存旧 `ra`、`sp`、`s0` 至 `s11`，再按相同布局载入新值。最后的 `ret` 使用恢复后的 `ra`，因而能够转入新线程的续执行位置。这里的调用符合 C 函数调用约定，调用者保存寄存器的跨调用需求由调用方处理。

6. **维持切换期间状态一致。** `schedule` 与 `proc_run` 的临界区保护覆盖选择、当前线程指针变更和实际切换。线程切出时，尚未执行完的 C 函数调用和局部变量继续保留在自己的内核栈上。当它以后被重新选中，会从先前的 `switch_to` 调用点之后继续执行，再按保存的状态恢复中断。初次运行的线程通过模块二构造的陷阱帧设置进入正常执行时的中断状态。

寄存器在 RV64 的 `struct context` 中按下表组织，每个槽位占 8 字节。

| 寄存器 | 字段偏移 | 切换时的意义 |
|------|------|------|
| `ra` | 0 | 指定函数调用的返回位置，首次切入时指向 `forkret` |
| `sp` | 8 | 选择目标线程的内核栈 |
| `s0`、`s1` | 16、24 | 保存被调用者保存寄存器的值 |
| `s2` 至 `s11` | 32 至 104 | 保存其余被调用者保存寄存器的值 |

假设链表中按顺序存在 A、B、C 三个普通线程，当前正在运行 A，且三者都可运行，那么一次选择会从 A 的后一项开始找到 B。B 再次发起调度时可以选到 C。如果 B 处于睡眠状态，扫描会跳过它并继续检查 C。调度顺序由当前节点位置和各线程状态共同决定。

模块三使用模块二已经建立的 PCB 和初始现场。普通线程第一次被选中时进入 `forkret`，已经运行过的线程则返回原先的调度调用路径。评分测试通过两个线程反复主动让出 CPU，再检查它们的执行标记，验证线程能够轮流获得执行机会。

## 六、实验总结与收获

### 对操作系统的理解

#### 重要知识点及其与 OS 原理的联系

1. **虚拟地址空间与分页管理。** OS 原理中的分页机制把虚拟地址分解为页号和页内偏移，由页表确定对应的物理页面。实验中的 `get_pte` 沿 Sv39 页表查找叶子项，`page_insert` 和 `page_remove` 修改映射关系。具体实现让我们看到，建立映射既涉及物理页，也涉及存放页表本身的页面，二者都需要申请和管理。

2. **共享资源与引用计数。** 一个物理页可以同时出现在多个虚拟地址的映射中。引用计数把这些映射与页面生命周期联系起来，删除一次映射便减少一次引用，最后一个引用消失后再回收。实验中“同页重复插入”和“替换成另一页”具有不同计数变化，通过这两个场景可以理解资源身份与资源使用次数之间的关系。

3. **页表和 TLB 的一致性。** TLB 利用地址访问的局部性减少页表遍历次数。当映射或权限发生变化时，缓存中旧的翻译可能继续生效，因此要执行 `sfence.vma`。这一过程把软件维护的数据结构与处理器内部的翻译状态联系起来，也说明了页表更新需要明确的同步时机。

4. **进程控制块与线程资源。** PCB 将编号、状态、父子关系、栈和地址空间集中记录，使内核可以统一管理线程。实验中的内核线程共享页表，各自拥有内核栈和上下文。它体现了 OS 原理中执行资源和地址空间资源的组织方式，`current` 则把当前 CPU 的执行状态与相应 PCB 关联起来。

5. **上下文切换与函数调用约定。** `struct context` 中的寄存器由 `switch_to` 按布局保存和恢复，调用栈中的局部数据随栈指针一起切换。`ra` 决定恢复后从哪里继续执行。首次启动时，人工构造的 `context` 和 `trapframe` 共同建立入口，这让我们理解了线程切换在机器指令层面如何实现。

6. **调度策略与执行机制。** 调度策略决定选择哪个可运行线程，执行机制完成地址空间和寄存器切换。实验通过 `schedule`、`proc_run` 与 `switch_to` 分别承担这些职责。将来更换优先级或时间片算法时，可以在保留底层切换接口的基础上调整选择逻辑。

7. **临界区与资源生命周期。** PID 分配、链表登记、线程计数和状态更新共同描述线程是否已经进入系统。把这些操作放在适当的临界区中，可以保持它们的一致性。创建失败时按照资源取得顺序反向释放，又体现了操作系统管理有限资源时对完整生命周期的要求。

#### OS 原理中重要但本实验尚未完整涉及的内容

1. **用户进程与地址空间隔离。** 完整的用户进程管理还包括用户页表、用户栈、可执行文件加载、系统调用和权限检查。本实验的内核线程共享启动页表，后续可以在现有 PCB 与创建流程上继续加入独立用户地址空间。

2. **时间片抢占与复杂调度算法。** 当前调度根据链表顺序选择可运行线程，测试线程主动调用调度函数。时间片调度还需要时钟中断维护运行时间并触发重新调度，优先级、多级反馈队列等策略则要增加相应的队列与统计信息。

3. **阻塞、等待与进程退出。** 完整生命周期需要把睡眠原因、事件唤醒、父进程等待、退出码和僵尸回收联系起来。本实验主要实现创建和切换，后续还需让 `do_exit` 配合等待机制释放线程资源，并处理父子进程关系。

4. **按需分页与写时复制。** 页表操作为这些功能提供基础接口，完整实现还要结合缺页异常、页面内容保存、权限变化和换入换出策略，使物理内存能够按实际访问需求分配。

5. **多核同步与跨核地址翻译一致性。** 多个 CPU 同时访问进程链表或更新页表时，需要锁、每 CPU 状态及跨核通知。局部中断控制服务于当前处理器上的临界区，跨核共享资源还需要进一步的同步机制。

### AI 协作开发的经验

1. **按模块推进更容易理解整体实现。** 页表操作、线程创建和调度分别承担明确的职责。围绕一个模块讨论实现，再沿调用关系检查它与前后模块的连接，能够逐步建立完整认识。尤其是线程创建与首次切入，两个阶段需要放到同一条执行路径中才能理解。

2. **围绕状态变化讨论代码更有效。** 对页面记录映射前后的引用计数，对线程记录创建前后的状态、栈和链表位置，可以把较长的代码转化为几次明确的变化。与 AI 一起分析这些变化时，也更容易定位哪一步应当分配资源、更新字段或释放旧对象。

3. **典型场景有助于检查实现细节。** 同页重复映射、删除不存在的映射、内核栈分配失败以及只有一个可运行线程，都能帮助理解不同分支的作用。为每个场景先写出期望的状态，再逐段检查代码，使讨论更具体，也让我们对边界条件有了更清楚的认识。

4. **C 代码和汇编需要结合阅读。** `copy_thread` 中设置的返回地址最终由 `switch_to` 使用，陷阱帧中的函数参数则经过恢复路径传到 `kernel_thread_entry`。把结构体字段、寄存器和调用位置对应起来后，原本分散在多个文件中的代码就能连成一条清晰的运行过程。

5. **运行结果可以帮助缩小排查范围。** 编译阶段关注类型和符号，启动阶段关注初始化顺序，评分阶段关注对应功能是否完成。按执行阶段阅读输出，可以更快找到应该检查的文件和函数。三项评分分别对应页表、创建和调度，也方便将观察到的结果与具体实现联系起来。

6. **复述实现过程能够巩固理解。** 完成一个模块后，用自己的话解释参数代表什么、资源怎样取得、失败时怎样退出，以及下一层如何使用结果，可以发现理解中的空缺。AI 提供了代码讨论和梳理思路的帮助，我们则通过阅读实际实现和运行结果逐步掌握这些机制。
