# Lab1：从启动原理到调试验证的提示词演进


学习主线：**建立启动时序 → 澄清地址与加载职责 → 理解固件接口 → 阅读字符输出代码 → 理解构建过程 → 定位环境差异 → 用调试证据验证原理。**

## 一、从“加电复位”建立启动时序

**原始提问：**“什么是加电复位？是将PC设置为0x1000吗？这一整步依赖哪些程序实现？”

最初关注的是 CPU 从哪里开始执行，以及实验源码是否参与这一步。提问需要先区分宿主机上运行的 QEMU 与模拟 CPU 正在执行的代码。

```text
背景：我正在学习 QEMU virt 平台上的 RISC-V 最小内核。讲义描述：
模拟 CPU 从 0x1000 开始执行复位代码，再进入位于 0x80000000 的 OpenSBI。

任务：
1. 解释“加电复位”的含义，说明它是否等同于设置 PC。
2. 区分真实硬件复位与 QEMU 对复位行为的模拟。
3. 说明复位代码、OpenSBI、entry.S 分别由谁提供、在什么时候执行。
4. 判断 lab1/code 在这一阶段参与的是构建、加载配置，还是指令执行。

输出要求：按时间顺序解释，并标明每一步由宿主机程序还是模拟 CPU 完成。
不要把本平台的 0x1000 描述成所有 RISC-V 处理器统一规定的地址。
```

**理解推进：**从“复位就是设置 PC”推进到区分机器初始状态、复位代码和内核入口，建立后续讨论的时间顺序。

## 二、从启动时序追问链接地址与加载地址

**原始提问：**“所以0x80200000是opensbi默认的，lab1/code/tools/kernel.ld与这件事又有什么联系呢？”“我对整个过程的发生顺序现在有点混乱了。”

有了启动链后，新的疑问是：为什么链接脚本和启动流程都出现同一个地址，它们是否存在直接调用关系？

```text
背景：kernel.ld 将内核按 0x80200000 布局；讲义也把该地址称为内核入口。
我目前把流程理解为两部分：构建内核镜像，以及 QEMU 启动模拟机器。

请检查这个理解，并回答：
1. 编译、链接、生成镜像、加载镜像和执行镜像的先后顺序是什么？
2. kernel.ld 由哪个工具读取？它是否负责把镜像放入模拟内存？
3. 0x80200000 是 CPU 固定要求、固件配置，还是本实验启动方案的约定？
4. 链接地址、实际加载地址和 CPU 最终执行入口为什么需要匹配？

请以本项目的 bin/kernel 与 bin/ucore.img 为例，画出文字流程，
再用一个符号地址的例子解释“按某地址链接”与“加载到某地址”的区别。
```

**理解推进：**将“内核知道自己在哪里”的模糊理解，细化为链接器计算地址、加载器放置字节、固件移交执行权三个环节。

## 三、核对讲义中的加载职责与 bootloader 含义

**原始提问：**“kernel image加载到（模拟的）物理内存这件事，并不是由opensbi实现？那opensbi的工作是什么？”“这个bootloader到底是不是opensbi？”

这一阶段不再只接受启动流程描述，而是对照讲义与实际启动参数，追问不同程序的职责边界。

```text
背景：讲义称 OpenSBI 为 bootloader，并描述它把内核加载到 0x80200000；
另一处又说内核被放入 QEMU 模拟的硬盘。项目使用的参数却是：
-device loader,file=$(UCOREIMG),addr=0x80200000

任务：
1. 结合该参数，判断是谁读取宿主机的镜像文件、谁将字节放入模拟内存。
2. 区分 QEMU 的 loader 功能与作为固件的 OpenSBI。
3. 解释 OpenSBI 除交接执行位置外，还承担哪些初始化和运行时职责。
4. 说明从 M 模式进入 S 模式为何不能只理解为修改 PC。
5. 判断“加载到模拟硬盘”的描述是否适用于当前命令。

要求：以当前配置为边界，必要时核对官方文档；区分已确认事实与推断，
不要把当前实验的加载方式推广为所有 OpenSBI 启动方案。
```

**理解推进：**区分“文件加载”与“系统引导”，并认识到启动内核还涉及特权级、运行环境和启动参数，而不只是一次地址跳转。

## 四、从 OpenSBI 职责深入到 SBI 调用机制

**原始提问：**“SBI服务是什么？内联汇编又是什么？二者有什么关系？”

在明确 OpenSBI 不只是启动时使用后，进一步阅读 libs/sbi.c，理解内核如何在运行中请求固件服务。

```text
背景：我正在阅读 libs/sbi.c，其中 sbi_console_putchar 调用 sbi_call，
sbi_call 使用 __asm__ volatile 设置寄存器并执行 ecall。

请围绕这份代码解释：
1. SBI 接口与 OpenSBI 实现之间的关系。
2. 什么是 C 内联汇编，它与独立的 entry.S 文件有什么区别。
3. 服务编号、参数和返回值分别如何在 C 变量与寄存器之间传递。
4. %[arg0]、输入输出约束及 volatile 各表示什么。
5. 以输出字符 'A' 为例，串起 S 模式内核发起请求、M 模式固件处理、
   返回内核的过程。

要求：按本项目实际使用的 SBI 调用方式解释，不混用其他版本的接口约定；
将“接口规定”与“内联汇编实现调用的手段”分开说明。
```

**理解推进：**从认识固件提供服务，深入到理解 C 函数封装、寄存器传参、ecall 与特权级切换如何组成一次调用。

## 五、沿字符输出路径理解接口分层与 C 语义

**原始提问：**“简单说明为什么这么命名sbi_console_putchar、cons_putc”“这里的console指得是？”“传入的参数是int，中间怎么变成了char，这是由谁实现的？”

对 SBI 的理解继续向上连接到 console.c：为什么同样输出字符，却存在不同名称、不同参数类型的函数？

```text
背景：console.c 中有如下代码：
void cons_putc(int c) { sbi_console_putchar((unsigned char)c); }

请先简要拆解两个函数名，再说明：
1. console 在本实验中指什么，它与终端窗口、串口、shell 有什么区别。
2. cons_putc 与 sbi_console_putchar 分别属于哪一层，为什么保留两层接口。
3. (unsigned char)c 是由程序员指定、编译器实现的什么操作。
4. 用 65、321、-1 举例说明转换后的数值，并区分字符编码与数字字符串。

要求：先给直接答案，再结合实际输出路径说明；只解释代码，不修改源文件。
```

**原始追问：**“while ((c = *str++) != '\0')这个循环条件没看明白”“什么功能”

```text
背景：我在 stdio.c 中读到 cputs：它循环执行
while ((c = *str++) != '\0')，调用 cputch(c, &cnt)，
最后输出 '\n' 并返回 cnt。

请分两层解释：
1. 语法层：将循环条件拆为读取字符、推进指针、赋值和判断结束的步骤。
   说明 *str++ 的结合方式，以及 '\0' 与字符 '0' 的区别。
2. 功能层：说明整个函数的输入、输出、副作用和返回值。
   用 cputs("Hello") 展示实际输出及计数，说明是否计入结束符和换行符。

要求：给出便于初学者理解的展开写法，并说明 const char * 为什么仍允许 str++。
```

**理解推进：**从底层服务向上理解接口封装，再回到具体 C 表达式，建立“字符串遍历 → 单字符输出 → SBI 请求”的联系。
