## 一、实验目的

本实验围绕“内核如何响应中断与异常，并在处理后继续执行”展开。在前面实验已经完成内核启动和物理内存管理的基础上，建立从 Trap 发生、保存现场、进入处理函数到恢复现场并返回的完整流程。主要目标如下：

1. 理解 RISC-V 中 Trap、中断和异常的关系，区分异步的时钟中断与同步的非法指令、断点异常，理解 M、S、U 特权级及中断委托机制的作用。
2. 掌握 `stvec`、`sstatus`、`sepc`、`scause` 和 `stval` 等寄存器在 Trap 过程中的职责，明确哪些状态由硬件自动记录，哪些寄存器需要由软件保存和恢复。
3. 理解 `struct trapframe` 的内存布局，补全 `RESTORE_ALL` 和 `__alltraps`，使汇编入口能够按照 RISC-V 调用约定把现场传递给 C 语言处理函数，并通过 `sret` 正确返回。
4. 理解中断与异常的分类处理，实现时钟事件续设、计数与输出，以及非法指令和断点异常的识别与返回位置调整，形成完整的 Trap 处理机制。
5. 理解全局中断使能、特定中断源使能和临界区保护之间的关系，认识引入异步中断后，内存管理等共享状态为什么需要保护。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

Lab 3 围绕中断和异常的处理展开，主要解决内核如何保存当前状态、处理事件并恢复执行的问题。Lab 2 提供了物理内存管理基础，本实验在此基础上建立 Trap 处理流程。时钟中断由定时器触发，非法指令和断点异常由当前执行的指令触发，它们都通过统一的 Trap 入口进入内核处理。

在 RISC-V 中，中断和异常统称为 Trap。OpenSBI 运行在 M 模式，实验内核运行在 S 模式。M 模式通过 `mideleg` 和 `medeleg` 将相应中断和异常委托给 S 模式处理。本实验中的 Trap 主要发生在内核运行期间；设置定时器时，内核通过 SBI 接口执行 `ecall`，进入 M 模式的 OpenSBI 完成服务，再返回 S 模式继续运行。

整个过程由硬件和软件共同完成。进入 S 模式处理 Trap 时，硬件记录 `sepc`、`scause`、`stval`，更新 `sstatus` 中的 `SPIE`、`SIE`、`SPP`，再跳转到 `stvec` 指定的入口。入口处的汇编代码将通用寄存器和相关 CSR 保存到内核栈，形成 Trap frame，再把它交给 C 函数。C 层根据事件原因进行处理，汇编层从这份 Trap frame 恢复状态，最后通过 `sret` 返回。

结合工程代码，主要执行关系如下：

```text
entry.S → kern_init()
    清零 BSS、读取设备树、初始化控制台
    → idt_init() → pmm_init() → idt_init()
    → clock_init() → intr_enable() → 内核继续执行

发生交由 S 模式处理的 Trap
    ↓ 硬件记录原因和返回位置，跳转至 stvec
__alltraps
    → SAVE_ALL：在内核栈上建立 trapframe
    → a0 = sp，调用 trap(tf)
        → trap_dispatch(tf)
            ├─ interrupt_handler(tf)：中断分类、时钟事件处理
            └─ exception_handler(tf)：异常分类、必要时调整 tf->epc
    → __trapret
        → RESTORE_ALL：恢复 CSR 和通用寄存器
        → sret：恢复执行位置及相应特权级、中断使能状态
```

两个功能模块通过 `trapframe` 配合。功能一负责保存、传递和恢复现场，功能二负责处理中断与异常，并确定后续执行位置。以断点异常为例，异常处理函数输出信息后修改 `tf->epc`，返回阶段将这个值写入 `sepc`，程序便从断点指令之后继续执行。这样，一份 Trap frame 就连接起了入口、处理和返回三个阶段。

### 3.2 功能的逐步实现

1. **衔接 Lab 2 的内存管理基础。** 将之前完成的物理内存初始化和分配器代码更新到 Lab 3 的对应位置，为内核启动和后续功能提供支持。引入中断后，`alloc_pages()`、`free_pages()` 通过外层的中断保护完成页分配和释放。

2. **建立统一入口，理解 `idt_init()`。** 该函数将 `sscratch` 初始化为 0，并把四字节对齐的 `__alltraps` 地址写入 `stvec`，采用 Direct 模式，使交给 S 模式处理的中断和异常进入同一汇编入口。初始化时先设置入口，再配置时钟并打开中断，使到来的事件能够进入相应处理流程。

3. **建立上下文管理，理解 `SAVE_ALL`、`__alltraps`、`RESTORE_ALL` 和 `__trapret`。** `SAVE_ALL` 将通用寄存器和 Trap 相关 CSR 整理成 `struct trapframe`；`__alltraps` 把其地址放入参数寄存器 `a0`，调用 `trap(tf)`。处理结束后，`RESTORE_ALL` 按原布局读取现场，`__trapret` 中的 `sret` 完成返回。我理解这部分的关键是汇编偏移与 C 结构体字段一一对应，并在其他寄存器恢复完成后，最后恢复作为访问基址的 `sp`。

4. **区分事件类别，理解 `trap()`、`trap_dispatch()` 及两个处理函数。** `trap()` 是 C 层统一入口，`trap_dispatch()` 通过 `tf->cause` 的最高位区分中断和异常。代码将其转换为 `intptr_t` 后判断是否小于 0，再分别调用 `interrupt_handler()` 或 `exception_handler()`。前者按中断编号处理时钟等来源，后者按异常编号处理非法指令、断点等情况。例如，`scause` 的中断标志为 1、编号为 5 时表示 S 模式时钟中断；标志为 0、编号为 2 和 3 时分别表示非法指令和断点异常。对于其他情况，`print_trapframe()` 输出寄存器、返回地址和事件原因，帮助分析现场。

5. **形成连续的时钟事件，理解 `clock_init()`、`clock_set_next_event()` 和 `intr_enable()`。** `clock_init()` 打开 `sie` 中的时钟中断源，设置第一次事件，并将 `ticks` 清零；`intr_enable()` 设置 `sstatus.SIE`，使当前 S 模式执行期间可以响应已使能的中断。`clock_set_next_event()` 调用 `get_cycles()`，通过 `rdtime` 读取时间计数器，再用 `sbi_set_timer()` 设置下一次触发时刻。按手册所用 QEMU 的 10 MHz 时间基准和代码中的 `timebase = 100000`，设定间隔约为 10 ms。每次处理时钟中断时，续设下一次事件并将 `ticks` 加 1，在 `TICK_NUM` 的整数倍处输出统计信息，累计输出达到要求后调用关机接口。通过这样的重复设置，内核持续收到时钟中断。

6. **确定异常后的执行位置，理解 `tf->epc` 的作用。** 非法指令和断点异常的 `epc` 指向触发异常的指令。按照本实验的处理要求，输出相应信息后，根据指令长度将 `tf->epc` 增加 2 或 4，使返回后继续执行后续代码。时钟中断处理则保留原来的执行位置。具体返回地址由 C 层处理函数确定，再通过 Trap frame 交给汇编恢复代码。

7. **保护共享状态，理解 `local_intr_save()`、`local_intr_restore()` 和原子位操作。** `local_intr_save()` 调用 `__intr_save()` 记录原有 `SIE`，并在原来允许中断时将其关闭；`local_intr_restore()` 根据保存的标志恢复中断使能状态。嵌套使用时，每一层都保存自己的进入状态，内层结束后仍沿用外层的中断设置。`do { ... } while (0)` 使保存宏在语法上表现为一条完整语句，便于放入条件分支。`alloc_pages()` 和 `free_pages()` 通过中断保护完成空闲链表及计数的更新，`atomic.h` 中的 `set_bit()`、`clear_bit()` 等则通过 RISC-V AMO 指令完成单个位的原子修改。

### 练习：[功能模块一：Trap上下文恢复与Trap功能入口]

**负责人：** [2410867-于润泽]

#### 模块功能描述

**需要实现的函数：**

本模块在 `kern/trap/trapentry.S` 中补全 `RESTORE_ALL` 汇编宏和 `__alltraps` 入口。

| 实现项 | 形式 | 对外作用 |
|------|------|------|
| `RESTORE_ALL` | 汇编宏 | 从当前 Trap frame 恢复处理器返回所需的状态 |
| `__alltraps` | 全局汇编入口标签 | 保存现场后，按调用约定将 Trap frame 传给 C 层 |

与本模块衔接的已有 C 接口为：

```c
void trap(struct trapframe *tf);
```

**功能说明：**

我负责的模块位于硬件 Trap 入口与 C 语言处理逻辑之间，负责将保存的现场传给 C 函数，并在处理结束后恢复执行环境。实现沿用教师提供的 `SAVE_ALL`、`struct trapframe` 和 `trap()` 接口，与后续的时钟和异常处理配合。

**（1）先确认 Trap frame 的布局。**

`struct trapframe` 的前一部分是按 `x0` 到 `x31` 顺序排列的 `struct pushregs`，后一部分依次是 `status`、`epc`、`badvaddr`、`cause`。当前 RV64 环境下，`REGBYTES` 为 8，因此整个结构占 36 × 8 = 288 字节。保存和恢复代码都按这组偏移访问各个字段，C 函数也通过同一布局读取现场。

| 相对于当前 `sp` 的偏移 | 内容 | 使用方式 |
|------|------|------|
| `0 * REGBYTES` | `x0` | 恒为零，不需要恢复 |
| `1 * REGBYTES` | `x1 / ra` | 恢复被打断执行流的返回地址寄存器 |
| `2 * REGBYTES` | Trap 发生前的 `x2 / sp` | 最后恢复，回到原栈位置 |
| `3 * REGBYTES` 至 `31 * REGBYTES` | `x3` 至 `x31` | 按对应偏移恢复通用寄存器 |
| `32 * REGBYTES` | `status` | 写回 `sstatus` |
| `33 * REGBYTES` | `epc` | 写回 `sepc`，采用处理后的返回地址 |
| `34 * REGBYTES` | `badvaddr` | 保留异常附加信息，供处理与诊断使用 |
| `35 * REGBYTES` | `cause` | 保留 Trap 原因，供分类与诊断使用 |

`SAVE_ALL` 首先把原 `sp` 放入 `sscratch`，再让栈向低地址扩展 288 字节，此时 `sp` 指向新建的 Trap frame。接着，代码通过 `csrrw s0, sscratch, x0` 取回扩展前的栈指针，同时清零 `sscratch`，再将取出的值放入第 2 号槽位。`s0` 等寄存器的原值已在前面的保存步骤中写入各自槽位，随后便可用于暂存 CSR。

**（2）通过 `__alltraps` 完成汇编到 C 的交接。**

`SAVE_ALL` 执行后，当前 `sp` 就是 Trap frame 的首地址。按照 RISC-V 调用约定，第一个参数通过 `a0` 传递，因此补充的入口代码为：

```asm
mv a0, sp
call trap
```

C 函数通过这个地址访问栈上的 Trap frame，对 `tf->epc` 等字段的修改会保留到返回阶段。调用时使用的 `a0`、`ra`，其原值已保存在 Trap frame 中。C 函数返回时按调用约定恢复自身使用的栈空间，使 `sp` 重新指向 Trap frame。原内核栈按 16 字节对齐，分配的 288 字节也是 16 的倍数，因此调用时保持了所需的栈对齐。

`trap()` 返回后，执行流顺序到达 `__trapret`，接着执行 `RESTORE_ALL` 和 `sret`，完成本次 Trap 的返回。

**（3）通过 `RESTORE_ALL` 恢复现场，并处理恢复顺序。**

实现先使用 `t0`、`t1` 读取保存的状态和返回地址，并写回相应 CSR：

```asm
LOAD t0, 32*REGBYTES(sp)
LOAD t1, 33*REGBYTES(sp)
csrw sstatus, t0
csrw sepc, t1
```

随后按原槽位恢复 `x1` 和 `x3` 至 `x31`。`t0`、`t1` 分别对应 `x5`、`x6`，在写完 CSR 后也会从自己的槽位恢复原值。恢复代码读取的 CSR 字段是 `status` 和 `epc`，`cause`、`badvaddr` 则供 C 层分类和分析事件使用；`x0` 在整个过程中保持为零。

最后才恢复 `sp`：

```asm
LOAD x2, 2*REGBYTES(sp)
```

前面的加载都以当前 `sp` 为 Trap frame 基址，因此将 `sp` 的恢复安排在最后。执行这条指令时，处理器先用当前 `sp` 计算源地址，再将取出的原栈指针写入 `x2`。这一步完成后，栈指针回到 Trap 发生前的位置，本次 Trap frame 占用的栈空间也随之释放。

**（4）理解 `sret` 与具体处理策略的配合。**

`__trapret` 在 `RESTORE_ALL` 之后执行 `sret`。`sret` 根据 `sepc` 恢复执行位置，根据 `sstatus.SPP` 决定返回特权级，并把 `SPIE` 保存的中断使能状态恢复给 `SIE`。本实验中，Trap 主要发生在 S 模式内核运行期间，保存的 `SPP` 记录了这一状态，返回时据此继续在 S 模式执行。

时钟中断返回时沿用保存的执行位置，非法指令和断点异常则由异常处理函数根据指令长度调整 `tf->epc`，恢复宏负责将处理后的值写入 `sepc`。通过这部分实现，我对上下文恢复的理解更具体了：Trap frame 保存执行状态，调用约定完成汇编与 C 的交接，返回代码再依据处理后的状态恢复运行。

## RESTORE_ALL
Pre-Condition:
- sp 指向由 SAVE_ALL 建立的有效 Trap frame。
- C 层处理已结束，现场中的返回地址和状态已准备好。

Post-Condition:
- sstatus 和 sepc 分别恢复为当前现场中的 status 和 epc。
- x1 至 x31 恢复为对应槽位的值，x0 保持为零。

  Case 1：C 层保留原返回地址。
  将现场中保存的 epc 写入 sepc，供 sret 继续原执行流。

  Case 2：C 层已调整返回地址。
  将调整后的 epc 写入 sepc，供 sret 从相应位置继续执行。

- 恢复过程始终按照 SAVE_ALL 使用的槽位访问现场。
- 用于暂存 CSR 的通用寄存器最终恢复为对应槽位的值。
- 在其他寄存器读取完成后恢复 sp，完成本次栈空间的释放。
- 使用现场中记录的特权级和中断使能状态完成返回准备。

Pre-Condition:
- 处理器已进入 S 模式 Trap 入口，相关 CSR 保存本次事件的信息。
- 当前内核栈空间充足，且满足调用约定的对齐要求。

Post-Condition:
- SAVE_ALL 完成现场保存，Trap frame 首地址作为参数传给 trap()。
- C 层处理和汇编返回阶段访问同一份 Trap frame。
- trap() 正常返回后进入 __trapret，执行上下文恢复和 sret。

Requirements:
- 完成现场保存后再设置参数并调用 C 函数。
- 调用过程保持栈对齐和 Trap frame 的完整性。
- 保持现有入口、保存宏和返回代码之间的执行顺序。

## 六、实验总结与收获

#### 重要知识点及其与 OS 原理的联系

1. **中断与异常体现了操作系统对执行流的管理。** OS 原理中，中断使操作系统能够响应外设和时间事件，异常则反映当前指令引发的特殊情况。在 RISC-V 中，两者统称为 Trap。Lab 3 通过 `scause` 的中断标志与原因编号识别事件，再用统一入口和分类处理函数组织代码，让我们将教材中的概念对应到了实际执行过程。

2. **上下文保存与恢复由硬件和软件共同完成。** 原理课常用“保存现场、处理中断、恢复现场”概括整个过程。本实验中，硬件记录执行位置、原因和特权状态，汇编保存通用寄存器，C 函数处理事件，最后由汇编与 `sret` 恢复执行。我们通过 Trap frame 的 36 个槽位，看清了各部分状态具体存放在哪里，以及处理结束后如何将它们还原。

3. **上下文管理是进程切换的基础。** OS 原理中的进程切换，需要先保存当前进程的运行状态，再恢复下一个进程的状态。本实验在处理 Trap 时保存寄存器和执行位置，处理结束后恢复原来的内核执行流。这个过程帮助我们理解了“保存后还能继续运行”的实现方式，也为后续学习进程调度和上下文切换打下了基础。

4. **返回位置体现了不同事件的处理方式。** 本实验处理非法指令和断点异常时，根据指令长度调整 `epc`，让程序从后续指令继续；时钟中断处理后，则按保存的位置恢复执行。对应到 OS 原理，缺页处理可以在补齐页面映射后重新执行访存指令，严重错误也可以交由进程终止机制处理。通过这些例子，我们理解了事件处理结果与程序执行位置之间的关系。

5. **时钟中断为抢占和时间管理提供基础。** 原理课中的时间片轮转、超时唤醒等机制，都依赖操作系统定期获得控制权。Lab 3 通过设置下一次时钟事件、累计 `ticks` 和输出统计信息，展示了周期性进入内核的过程。结合 QEMU 的时间基准计算中断间隔后，我们也理解了时钟计数如何与时间联系起来，以及调度和超时机制可以如何使用这些计数。

6. **特权级和中断使能共同控制 Trap 的处理过程。** M、S、U 模式决定可执行的特权操作和资源访问范围，`SIE`、`sie` 控制中断响应。进入 Trap 时，硬件将原 `SIE` 保存到 `SPIE`，暂时关闭 S 模式中断，并用 `SPP` 记录进入前的特权级。执行 `sret` 时再根据这些状态完成返回。通过分析这些位的变化，我们理解了处理器如何在进入和退出 Trap 时衔接执行环境。

7. **中断保护把临界区的概念落实到了内存管理中。** OS 原理中的临界区，是对共享数据进行访问和修改的一段代码。本实验在页分配和释放外层保存并关闭本核中断，完成空闲链表和空闲计数更新，再恢复进入时的中断状态。`atomic.h` 中的 AMO 位操作则用于修改页面标志等状态。阅读这些代码后，我们对临界区的起止位置、保护的数据以及中断状态的保存方式有了具体认识。

在协作过程中，我们先梳理各模块的接口和 Trap frame 布局，再将进入时的状态、处理后的结果写进提示词。这样，分析代码时就能逐项检查寄存器槽位、`sp` 的恢复顺序以及 `epc` 的传递过程。两个模块共用同一份现场，也让我们体会到提前约定数据结构和接口对分工合作的帮助。

#### OS 原理中重要但本实验尚未完整涉及的内容

1. **完整的用户进程与系统调用。** 用户进程需要程序加载、用户栈和内核栈管理等支持。系统调用还包括调用号分发、参数检查和返回值传递。本实验介绍的 U 模式到 S 模式的 Trap 过程，是后续实现这些功能的基础。

2. **进程调度与完整的进程上下文切换。** 在时钟中断和现场管理的基础上，调度器还需要维护 PCB、就绪队列和时间片，处理进程的阻塞与唤醒，并在切换进程时更换相应执行状态和地址空间。这些机制共同完成多个进程之间的 CPU 分配。

3. **可恢复的虚拟内存异常。** 缺页处理需要根据出错地址分配页面或加载数据，建立页表映射后重新执行相关指令。请求分页、页面置换和写时复制也会使用这一机制，将异常处理与虚拟内存管理联系起来。

4. **完整的设备中断与 I/O 子系统。** 完整的外设中断处理包括中断控制器的请求确认、设备状态读取和处理完成通知。磁盘、网络等设备驱动还会涉及请求队列、DMA 和等待进程的唤醒，将设备产生的中断与具体 I/O 请求对应起来。

5. **复杂并发与多核同步。** 多核环境下，共享数据的访问需要结合自旋锁、原子指令和内存顺序进行组织；中断嵌套与优先级也会影响处理顺序。这些内容可以进一步扩展本实验对临界区和中断使能的认识，并帮助分析同步开销与中断响应时间。
